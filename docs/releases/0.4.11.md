# HomeDash 0.4.11

Cette version rend les interruptions visibles, collecte les données sans dépendre de la tablette et ajoute un redémarrage quotidien du Raspberry Pi à 03 h, heure de Paris.

## Connexion et diagnostic

- L’indicateur de la barre supérieure ouvre un diagnostic accessible sans PIN. Une bannière apparaît pour une tablette hors réseau, un Pi inaccessible, une erreur HTTP de HomeDash, une liaison temps réel interrompue ou des collectes externes en retard.
- Le Pi répond à une sonde indépendante toutes les 30 secondes. Le diagnostic montre la dernière réponse reçue, la dernière collecte réussie et la dernière tentative météo/calendrier. Un fournisseur inaccessible ne fait pas apparaître le Pi comme déconnecté.
- Une réponse absente ne permet pas de conclure que le Pi est éteint : réseau, DNS, Nginx, HomeDash ou système peuvent être en cause. Le guide [de diagnostic réseau](../pi-network-freeze-diagnostic.md) conserve son rôle pour les pannes SSH.
- Les requêtes expirent après 30 secondes, ou 8 secondes pour la sonde. La liaison WebSocket échange un heartbeat toutes les 20 secondes et se reconnecte si elle devient silencieuse, au réveil ou après une coupure. Un retour de connexion recharge les widgets.

## Collecte régulière et cache

- Le Pi collecte les positions météo de toutes les pages toutes les **10 minutes**, et les agendas toutes les **5 minutes**, même quand aucune tablette n’est connectée. La première collecte se lance au démarrage ; les widgets ajoutés sont pris en compte au passage suivant, dans les 30 secondes.
- Les positions/agendas identiques partagent leurs demandes, y compris le renouvellement OAuth. Le cycle de fond effectue ses requêtes à la suite pour limiter la charge du Pi Zero. Une panne du fournisseur déclenche une nouvelle tentative après une minute, sans multiplier les appels simultanés.
- La tablette lit la météo toutes les 10 minutes et les événements toutes les 5 minutes. Au déverrouillage Android, au réveil caméra, au retour dans l’application/l’onglet ou au retour du réseau, les widgets actifs demandent une actualisation immédiate. Calendar peut désormais contourner son cache sur ces demandes.
- Les dernières valeurs sont conservées sur le Pi et dans le stockage local de la tablette. Après fermeture/rechargement de l’interface, le cache tablette reste affichable si le Pi est inaccessible ; sa date d’origine est conservée et il est signalé comme périmé. Un stockage tablette plein ou indisponible n’empêche pas l’affichage des réponses reçues.
- Les erreurs de liaison et les données périmées sont visibles dans les widgets. Les prévisions dépassées restent identifiées comme expirées ; aucune nouvelle prévision n’est inventée après la fin de la période récupérée.

## Redémarrage quotidien

- Timer `homedash-nightly-reboot.timer` à **03:00 Europe/Paris**, avec adaptation au changement d’heure. Il ne rattrape pas une nuit manquée par un redémarrage en journée.
- Verrou partagé avec l’updater : si une installation ou un rollback est en cours, le redémarrage est ignoré cette nuit. Le service utilise le redémarrage normal de Linux.
- Journaux persistants et bornés pour examiner le démarrage précédent. Le timer est activé sur une nouvelle installation ; une désactivation explicite est conservée par les futures mises à jour.
- Ce redémarrage est une mitigation : un Linux complètement figé ne peut pas exécuter le timer. Il ne répare pas une alimentation, une carte SD ou un pilote défaillant.

## Versions, publication et transition

Serveur, interface Web, contrats et APK : **0.4.11**. Android : **versionCode 18**. Widgets météo et Calendar : **0.4.11**.

Assets attendus :

- `homedash-native-0.4.11.tar.gz` et `homedash-native-0.4.11.tar.gz.sha256` ;
- `homedash-kiosk-0.4.11.apk` et `homedash-kiosk-0.4.11.apk.sha256`.

Le push du tag `v0.4.11` déclenche le workflow Release existant : archive native, APK signée et publication GitHub. Le Pi installé avec un updater fonctionnel récupère la version applicative par sa boucle automatique de dix minutes. Android demande toujours la confirmation d’installation de l’APK.

**Une commande SSH unique reste nécessaire sur un Pi existant pour le nouveau service système.** Après publication de la Release et hors mise à jour en cours :

```bash
cd /opt/homedash/repository
git status --short
git fetch --tags origin
git checkout v0.4.11
sudo bash deployment/raspberry-pi-zero/install-reliability.sh
sudo systemctl list-timers homedash-nightly-reboot.timer --no-pager
```

Le checkout doit être propre. La migration met à jour le script privilégié, active le timer et la persistance des journaux, sans redémarrer le Pi ni changer les paramètres HomeDash. À partir de cette migration, les archives suivantes embarquent les fichiers de maintenance et l’updater les applique après un contrôle de santé réussi. Si l’installeur est antérieur à 0.4.5, utiliser plutôt `sudo bash deployment/raspberry-pi-zero/install-native.sh v0.4.11`.

Voir [le guide de mise à jour](../updates.md) pour les commandes commit/push/tag, la réparation et la désactivation du timer.

## Recette sur le matériel

Vérifier la CI et le workflow Release, puis tester déverrouillage, réveil caméra, retour depuis Android, ajout d’un événement Google et actualisation en moins de cinq minutes. Avec une collecte autonome, l’âge des données doit avancer sans tablette ouverte. Couper temporairement le Wi-Fi tablette, puis rendre le Pi indisponible séparément : vérifier bannière, dates du cache, reprise automatique et absence de perte des brouillons. Recharger la page hors ligne après un premier chargement réussi. Vérifier le prochain timer, les journaux après 03 h et le retour de la tablette après reboot. Observer la stabilité du réseau et la mémoire pendant 48 heures ; les tests automatisés ne remplacent pas cette recette matérielle.
