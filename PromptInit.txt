# Projet : HomeDash - Dashboard domestique modulaire sur tablette Android

Ce document décrit la conception et le développement du projet libre et auto-hébergeable **HomeDash**.

Avant de commencer à coder massivement, analyse ce cahier des charges, inspecte l'environnement et le repository existant s'il y en a un, puis propose une architecture technique cohérente.

Tu peux remettre en question certains choix décrits ci-dessous si une meilleure solution existe, mais explique brièvement pourquoi avant d'effectuer un changement architectural important.

L'objectif est de construire d'abord un **MVP fonctionnel et propre**, tout en concevant dès le départ une architecture suffisamment modulaire pour faire évoluer le projet pendant plusieurs années sans devoir tout réécrire.

---

# 1. OBJECTIF GÉNÉRAL

HomeDash fournit un dashboard domestique affichable en permanence sur une tablette tactile, par exemple fixée au mur dans l'entrée d'un logement.

Matériel compatible visé :

* tablette Android 10 ou version ultérieure ;
* tablette fixée au mur ;
* tablette alimentée en permanence ;
* tablette entièrement dédiée au dashboard ;
* Raspberry Pi disponible sur le réseau local et pouvant fonctionner 24 h/24 ;
* ordinateur utilisé pour le développement ;
* Git/GitHub pour versionner et distribuer les nouvelles versions.

Le dashboard doit afficher différentes informations domestiques sous forme de **widgets/modules indépendants**.

Exemples :

* heure ;
* date ;
* météo ;
* prévisions météo ;
* températures intérieure/extérieure ;
* Google Calendar ;
* notes ;
* état du réseau ;
* informations système ;
* futurs capteurs domotiques.

Le système est destiné à être auto-hébergé par un foyer. Il n'est pas nécessaire de concevoir une infrastructure SaaS, multi-tenant ou destinée à des milliers d'utilisateurs.

Je privilégie :

1. simplicité ;
2. fiabilité ;
3. modularité ;
4. fonctionnement local ;
5. maintenance facile ;
6. faible consommation de ressources ;
7. sécurité ;
8. facilité d'ajout de nouveaux modules.

# 2. ARCHITECTURE ENVISAGÉE

L'architecture privilégiée est la suivante :

PC de développement
↓
Git / GitHub
↓
Raspberry Pi
↓
Application/dashboard local
↓
Tablette Android en mode kiosque

Le Raspberry Pi doit servir de serveur central.

Il hébergera notamment :

* le frontend du dashboard ;
* le backend/API ;
* les données persistantes ;
* les configurations ;
* les intégrations avec les services externes ;
* les intégrations avec les futurs capteurs ;
* le système de mise à jour ;
* éventuellement MQTT.

La tablette doit principalement servir de client/interface.

Je privilégie une architecture :

**Web application locale + application Android légère servant de conteneur/kiosque**

L'application Android pourrait charger le dashboard hébergé sur le Raspberry Pi via WebView ou une solution équivalente.

Cette couche Android doit uniquement être utilisée lorsqu'elle apporte quelque chose que le navigateur ne peut pas faire correctement :

* mode kiosque ;
* plein écran ;
* gestion écran allumé/éteint ;
* caméra/détection de présence ;
* informations système de la tablette ;
* communication native avec Android ;
* éventuellement démarrage automatique après reboot.

Si une meilleure architecture existe, propose-la et justifie-la.

---

# 3. FONCTIONNEMENT LOCAL

Le dashboard doit être conçu selon une approche **local-first**.

Il doit continuer à fonctionner sur le réseau local lorsque la connexion Internet est coupée.

Les fonctionnalités nécessitant Internet peuvent évidemment devenir temporairement indisponibles :

* Google Calendar ;
* récupération de données météo distantes ;
* recherche de mises à jour GitHub ;
* autres API Internet.

En revanche, doivent continuer à fonctionner :

* interface ;
* configuration ;
* widgets locaux ;
* notes ;
* données précédemment mises en cache ;
* capteurs locaux ;
* informations réseau ;
* navigation ;
* mode édition.

Le dashboard ne doit PAS dépendre d'un serveur cloud personnel.

# 6. MODE NORMAL ET MODE ÉDITION

Deux modes doivent exister.

## Mode normal

Interface propre.

Les widgets sont verrouillés.

Aucune poignée de redimensionnement ou bouton de suppression ne doit encombrer l'interface.

## Mode édition

Un bouton permet de passer en mode édition.

Dans ce mode, l'utilisateur peut :

* déplacer un widget par drag-and-drop tactile ;
* redimensionner un widget ;
* supprimer un widget ;
* ajouter un widget ;
* configurer un widget ;
* changer de page ;
* créer une page ;
* supprimer une page ;
* renommer une page.

La disposition doit être persistante.

Après redémarrage du Raspberry Pi ou de la tablette, le dashboard doit retrouver exactement sa configuration.

Prévoir un moyen simple d'annuler les modifications ou de restaurer une disposition précédente si cela reste raisonnable pour le MVP.

# 10. DÉTECTION DE PRÉSENCE

La tablette est branchée 24 h/24 mais son écran ne doit pas rester allumé en permanence.

Objectif :

aucune présence
→
écran éteint

personne détectée devant la tablette
→
écran allumé

aucune présence pendant environ 60 secondes
→
écran éteint

Le toucher de l'écran doit également pouvoir réveiller le système si Android le permet.

La caméra frontale peut être utilisée.

IMPORTANT :

Je ne veux PAS de reconnaissance faciale.

Je veux uniquement détecter la présence d'une personne ou un mouvement suffisamment fiable.

Le traitement doit être effectué localement.

Aucune image de caméra ne doit :

* être enregistrée ;
* être envoyée sur Internet ;
* être envoyée au Raspberry Pi sauf nécessité technique clairement justifiée.

Privilégier le traitement directement sur la tablette.

Étudier les contraintes Android 10 concernant :

* caméra en arrière-plan ;
* verrouillage/déverrouillage ;
* extinction réelle de l'écran ;
* permissions ;
* Device Admin / Device Owner ;
* mode kiosque ;
* WakeLock ;
* réveil de l'écran.

Ne contourne pas artificiellement les restrictions Android.

Si Android empêche une partie exacte du comportement demandé, explique la limitation et implémente l'alternative techniquement la plus propre.

La détection ne doit pas utiliser inutilement beaucoup de CPU ou de batterie.

→

→

→

→

IMPORTANT :

Je veux des mises à jour **manuelles**.

Le dashboard doit disposer d'une section :

**Paramètres → Mises à jour**

avec un bouton :

**Rechercher les mises à jour**

Le serveur vérifie alors le repository configuré.

Si aucune mise à jour :

"HomeDash est à jour."

Si une nouvelle version existe :

afficher par exemple :

Version installée : 0.1.0
Version disponible : 0.2.0

et éventuellement :

* date ;
* changelog ;
* commit/tag correspondant.

Puis bouton :

**Installer la mise à jour**

L'installation doit idéalement :

1. sauvegarder l'état/configuration nécessaire ;
2. récupérer la version ;
3. installer les dépendances si nécessaire ;
4. effectuer les migrations éventuelles ;
5. reconstruire le frontend ;
6. redémarrer les services ;
7. effectuer un health check ;
8. revenir automatiquement à l'ancienne version si la nouvelle version ne démarre pas correctement.

Éviter absolument un simple "git pull && restart" sans mécanisme de sécurité.

Étudier l'utilisation de :

* tags/releases Git ;
* versioning sémantique ;
* Docker/Docker Compose ;
* images/version précédente ;
* mécanisme de rollback.

Choisir la solution la plus simple et fiable pour un Raspberry Pi auto-hébergé.

Le système de mise à jour lui-même doit être conçu avec prudence afin qu'une mise à jour défectueuse ne rende pas le dashboard inutilisable.

# 20. CACHE ET GESTION DES ERREURS

Les widgets doivent gérer correctement les erreurs.

Exemple météo :

si Internet tombe, ne pas remplacer immédiatement le widget par une grosse erreur.

Afficher plutôt les dernières données connues avec :

et éventuellement une petite indication hors ligne.

Chaque widget doit pouvoir gérer :

* loading ;
* ready ;
* stale ;
* error ;
* offline.

Une erreur dans un widget ne doit jamais faire planter tout le dashboard.
